# Конвейер

NormGraph строит и поддерживает граф в два слоя — **структурный ингест** и **извлечение
ограничений** — связанных жизненным циклом **синхронизации**.

## 1. Структурный ингест (`src/ingestion`)

Без LLM; быстрый и идемпотентный.

1. Забрать документ из IDU_DVD: `GET /library/documents/{doc_id}` → собранный текст + упорядоченные
   фрагменты (пункты) с иерархией, тегами, привязкой к источнику и `references`.
2. Upsert `:Document` (`MERGE` по `doc_id`, `SET += props`, включая `content_hash`).
3. Upsert каждого `:Clause` (`MERGE` по `node_id`) и привязка `IN_DOCUMENT`.
4. Рёбра — после того как все пункты созданы:
   - `PART_OF` из `parent_id` фрагмента;
   - `REFERENCES` из `references` фрагмента; цель выбирается по тому, насколько IDU_DVD её разрешил:
     разрешённый id пункта → `:Clause`; разрешённый документ целиком → `:Document`; неразрешённая →
     заглушка `:PendingReference` (которая автоматически свяжется, когда целевой документ загрузят).
5. При `replace=True` (изменённый документ) пункты, исчезнувшие в новой версии, **удаляются** (вместе
   с производными от них ограничениями), чтобы после переингеста не осталось устаревших пунктов.
6. Связи фрагментов IDU_DVD (`GET /library/documents/{doc_id}/relations`) зеркалируются как
   `(:Clause)-[:DEPENDS_ON {weight, kind}]->(:Clause)` и заменяют прежние связи документа.
   Сохраняются только связи между пунктами этой версии. IDU_DVD без связей (404) или недоступный
   эндпоинт оставляют структурный слой без них.

Все записи — `MERGE` по естественным ключам, поэтому ингест документов в произвольном порядке (или
дважды) сходится к одному и тому же графу.

## 2. Извлечение ограничений (`src/pipeline`)

Работает по каждому пункту; нужны LLM и эмбеддер.

### Извлечение (langextract)

- `src/pipeline/prompts.py` — промпт и одобренные few-shot примеры (из СП 42.13330.2016) плюс
  стартовый словарь видов.
- `src/pipeline/extractor.py` запускает `langextract.extract(...)` по тексту пункта нашей моделью
  поверх провайдера (`src/providers/langextract_backend.py` направляет langextract через
  настроенный `LLMProvider`), затем маппит результат в `ExtractedRestriction`
  (`{subject, object, kind, value}` + offset'ы источника). langextract исполняется в рабочем потоке;
  пустые и некорректные ответы повторяются (до трёх попыток на запрос). Корректный пустой
  массив `extractions` принимается сразу. Ошибки разбора больше не подавляются библиотекой.

`value` кодируется плоскими строковыми атрибутами (`value_operator`/`value_number`/`value_unit`/
`value_condition`) и парсится обратно в структурированный `RestrictionValue`. Пункт с условными
нормами даёт несколько извлечений — по одному на значение.

Если попытки исчерпаны, пункт не записывается и попадает в `failed_clause_ids`; ответ содержит
`incomplete=true`, `reason=invalid_llm_output` и `warnings`. `clauses_processed` считает успешно
обработанные пункты, включая пункты без норм. Остальные нормы сохраняются. В графе перед началом
работы устанавливается `extraction_incomplete`; признак снимается только при полном успехе.
Синхронизация и стартовая сверка повторяют неполные документы даже при неизменном хеше.
Backfill сообщает частичный результат как failed с количеством сохранённых норм и предупреждениями;
его выборка по-прежнему ограничена документами без норм. Остальные документы можно повторить через
эндпоинт извлечения по doc_id. Повтор документа обрабатывает все пункты; внутри запуска повторяется
только запрос с ошибочным ответом. Не запускайте обработку одного документа одновременно.
Старые пропуски автоматически не обнаруживаются: такие документы нужно переизвлечь.

### Связанные пункты и ссылки (`clause_context.py`)

Пункт часто задаёт значение в другом месте: «по таблице 7.2», «в соответствии с п. 4.2.1», пункты
списка после вводной фразы «должно составлять:». Такие пункты называет граф:

- `REFERENCES` на пункт: ссылку разрешил IDU_DVD или NormGraph при загрузке документа. Внутренняя
  ссылка без номера пункта («таблицей 6.1 настоящих Нормативов», «пункт 4.2.1») привязывается к
  пункту с этим номером или к фрагменту «Таблица 6.1», если номер в документе единственный;
- `REFERENCES` на документ или неразрешённую ссылку — к пункту с указанным номером в документе
  NormGraph, название которого начинается с названия из ссылки («СП 42.13330» → «СП 42.13330.2016 …»);
- `DEPENDS_ON` — связи IDU_DVD с весом от 0,7, кроме `same_topic` (`completes`, `refines`,
  `table_ref`, `condition`, `exception`, `definition`).

IDU_DVD хранит таблицу заголовком («Таблица 6.1 …») и через несколько фрагментов телом (`kind=table`):
ссылка на заголовок получает и тело таблицы. Примечания о редакциях («(в ред. постановления …
N 1809-ПП)») связанными пунктами не считаются.
Экстрактор читает связанные пункты перед текстом пункта (до `NG_EXTRACTION_CONTEXT_CHARS` символов,
каждый до 800): так пункт списка получает объект и показатель из вводной фразы («— не более 250 м» —
пешеходная доступность до остановок). Отдельный блок инструкций в промпте давал пустой ответ, поэтому
контекст идёт тем же текстом. Нормы извлекаются из самого пункта: ограничение, цитата которого целиком
в связанном пункте, отбрасывается без ошибки — его даст свой пункт. Цитата может начинаться во
вводной фразе, если её конец (не меньше двух слов или чисел) — текст пункта. Значение, которого нет ни в
цитате, ни в пункте, принимается, только если оно есть в показанном связанном пункте; этот пункт
записывается в `value_source` нормы (`Restriction.value_source_json`). Ссылки, текста которых в
NormGraph нет (документ не загружен или пункт не найден), записываются в `unresolved_references` нормы
без числового значения — это кандидаты на загрузку в IDU_DVD.

Планировщик видит те же пункты: проходы переписывания и верификации получают их после текста пункта, а
проверка «число есть в источнике» учитывает их текст. Перепланирование читает их из графа, поэтому
«Перестроить все планы» использует связи без повторного извлечения. Новые связи появляются после
синхронизации документа с `replace=true` (структура обновляется), значения по ссылкам — после повторного
извлечения.

### Показатель, база расчёта и формирование плана

Названия сущностей (`subject`, `object`) отделены от показателя и базы расчёта. Извлекатель читает
плоские атрибуты `measurement_kind`, `measurement_indicator`, `measurement_basis`,
`measurement_numerator_entity`, `measurement_denominator_entity` в необязательную модель
`measurement`. Виды: `area_share`, `count_share`, `provision`, `distance`, `linear_size`, `other`.
«90% расчётного уровня автомобилизации» — база расчёта, а «для сельских поселений» — условие
применимости. В `extraction_text` сохраняется полное предложение, подтверждающее измерение.

В графе эти внутренние данные хранятся в `Restriction.measurement_json`; backfill и regenerate
восстанавливают их. Они участвуют в идентификаторе нормы, чтобы разные базы расчёта не сливались.
Старые нормы без метаданных остаются читаемыми.

`zonal_ratio` проверяет только отношение площадей. Нужны явные сущности числителя и знаменателя,
база-площадь и подтверждающая формулировка в исходном тексте. Числитель — площадь измеряемого
объекта; зона — территория, площадь которой принята за 100%. Проценты обеспеченности, потребности,
числа машин или населения сюда не подходят. Для старых процентных норм без описания измерения
нужно повторное извлечение; один regenerate возвращает `ratio_basis_not_supported`. Ширина,
высота и длина объекта не преобразуются в буфер расстояния между объектами.

Неподдерживаемые измерения и названия сущностей длиннее 200 символов дают план `unsupported`
с причиной (`unsupported_measurement`, `ratio_basis_not_supported`, `entity_label_too_long` и др.).
Названия и исходный текст не обрезаются; описание измерения и условия сохраняются в параметрах
заблокированного плана. Невалидные параметры детерминированного плана также дают `unsupported`.
Неожиданная ошибка планировщика изолируется для одной нормы, записывается как `planner_failed`
и в `ExtractResult.warnings`; следующие нормы продолжают записываться. Ошибки базы не скрываются.

Планировщик отклоняет показатели вместо объектов («расчётный радиус», «уровень доступности»),
радиусы разворота/диаметры, расстояния от входов и расстояния между однотипными объектами.
Причины: `non_spatial_entity`, `linear_size_not_distance`, `specific_geometry_required`,
`same_entity_spacing_not_supported`. LLM-проходы не могут обойти проверки или придумать новые
сущности для слоёв. Эти проверки не подтверждают наличие данных в Urban API.

После развёртывания затронутые планы нужно пересоздать. Новые поля измерения появятся после явного
повторного извлечения документа. Оно может изменить сущности, метаданные и идентификаторы норм;
по умолчанию старые нормы тоже сохраняются. Перед заменой документа проверьте существующие ревизии.
Развёртывание и стартовый backfill не мигрируют все планы автоматически: планы старой версии
планировщика перепланируются через `POST /check-plans/replan` (сначала dry run). Эти проверки консервативны
и не гарантируют правильность смысла произвольного ответа LLM.

### Виды ограничений (`src/pipeline/kind_taxonomy.py`)

Вид ограничения — один из **закрытого списка** из 20 видов, они хранятся как утверждённые узлы
`:RestrictionKind`: `запрет_размещения`, `запрет_использования`, `требование_размещения`,
`допустимость`, `минимальное_расстояние`, `максимальное_расстояние`, `время_доступности`,
`минимальный_размер`, `максимальный_размер`, `предельная_высота`, `минимальная_доля_площади`,
`максимальная_доля_площади`, `плотность_застройки`, `обеспеченность`, `количество`, `срок`,
`физический_параметр`, `требование_к_объекту`, `процедурное_требование`, `прочее`. Промпт
перечисляет их с пояснением и запрещает новые коды. Раньше модель придумывала вид всякий раз, когда
не подходил ни один из восьми исходных; так набрались сотни видов, большинство — по одной норме.

Метка, которую вернула модель, сохраняется в `kind_label` и сводится к виду из списка:

1. норма **с числом** получает вид своего показателя — по единице, measurement и метке:
   «не более 500 м» до остановки — `максимальное_расстояние`, даже если модель указала
   `минимальное_расстояние` или `требование_размещения`; цитата учитывается, только когда метка и
   единица ничего не говорят;
2. иначе вид из списка сохраняется, а придуманный сводится по словам метки
   (`запрет_пересмотра` → `запрет_использования`, `требование_схемы` → `процедурное_требование`);
3. несопоставленная метка сравнивается по эмбеддингу (косинус ≥ `NG_KIND_MATCH_THRESHOLD`) с видами
   списка; если и так нет совпадения — вид `прочее` с `kind_status="pending"`.

Нормы, извлечённые до закрытия списка, сводит кнопка «Свести виды и дубли» в админ-панели (см.
[admin](admin.md)) — без LLM, без смены идентификаторов и планов.

### Дубли норм (`src/pipeline/duplicates.py`)

Одна и та же норма извлекается несколько раз: новая редакция повторяет прежнюю (СП 2.4.3648-20 и
СП 2.4.2.4283-26 делят около двухсот норм), пункт перечня повторяется в нескольких разделах. Такие
нормы **сохраняются** — у каждой свой источник и план — и получают общий `duplicate_group`. Две
нормы общего корпуса — дубли, если у них одинаковый `norm_key` (канонические субъект и объект, вид,
значение с условием) и цитаты говорят одно (половина слов общая или большая часть короткой цитаты
входит в длинную). Норма вступает в группу своих дублей при записи; пользовательские документы не
группируются.

Поиск и `applicable` возвращают одну норму группы и перечисляют остальные в её `duplicates`
(`collapse_duplicates=false` возвращает каждую); карточка нормы тоже их перечисляет.

### Резолв/дедуп сущностей

Subject и object резолвятся в канонические `:Entity` тем же способом (точный → нечёткий ≥
`NG_ENTITY_MERGE_THRESHOLD`), с сохранением алиасов. Именно этот междокументный дедуп позволяет
ограничениям из разных документов связываться через `SHARES_ENTITY`. Полноценное хранилище терминов —
отложенный TODO; пока каноническая форма — первое встреченное нормализованное имя.

### Запись в граф (`src/pipeline/service.py`)

Для каждого извлечённого ограничения:

- резолв `kind`, `subject`, `object`;
- эмбеддинг текста `subject | object | kind [| value]` плюс предложение пункта (`extraction_text`) с
  отметкой `embedding_version`; векторы старой версии пересчитываются при старте;
- **детерминированный id** = хеш от `clause + subject + object + kind + value` (чтобы переизвлечение
  сходилось, а не дублировало);
- upsert `:Restriction` и рёбра `DERIVED_FROM`, `HAS_SUBJECT`, `APPLIES_TO`, `OF_KIND`;
- вступление в группу дублей той же нормы из других пунктов (`norm_key`, см. «Дубли норм»);
- пересборка `SHARES_ENTITY` со связанными ограничениями.
- построение версионированного `CheckPlan` многопроходным планировщиком (ниже); неразрешимая
  норма получает `planner_status=unsupported` с причинами.

План хранится отдельным `:CheckPlan` с неизменяемыми ревизиями и связью текущей
версии с `:Restriction`. Автоматическое переизвлечение не перезаписывает план со
статусом `reviewed`. Очередь экспертного ревью позволяет подтвердить, отклонить или
заменить план и фиксирует автора, комментарий и время. Старые ограничения без плана
остаются валидными и возвращаются без принудительной миграции.

### Многопроходный планировщик CheckPlan (`check_plan_planner.py`, `norm_*.py`)

План становится `auto`, только если его принял каждый включённый проход:

0. **Данные.** Красных линий в Urban API нет. Норма, которой они нужны («красная линия»,
   «линия (регулирования) застройки» в субъекте, объекте, цитате или слоях кандидата), получает
   `unsupported` с первой причиной `red_line_not_in_data`; LLM-проходы не запускаются, кандидат
   детерминированного прохода и остальные причины сохраняются для проверки. Проверка —
   `norm_guards.mentions_red_line`: когда красные линии появятся в данных, её нужно убрать и
   перестроить планы.

1. **Детерминированный.** Грамматика целого пункта (`spatial_rules.py`), затем разрешённый планировщик
   по тройке. Проверки точности (`norm_guards.py`) блокируют дефекты прода: метку-величину вместо
   слоя («отступ от красной линии», `non_spatial_entity` / `measure_label_as_entity`), максимум,
   прочитанный как минимум (`operator_direction_conflict`), шаг вдоль линии («не реже чем через
   100 м», `periodic_spacing_not_supported`), глубину (`depth_not_distance`), внутридомовой масштаб
   (`distance_below_territorial_scale`, меньше `NG_CHECK_PLAN_MIN_DISTANCE_M`) и доли частей здания.
2. **Привязка к каталогу.** Каждая сущность слоя — каноническое название Urban API (сервис,
   физический объект или код функциональной зоны) из `NG_URBAN_API_URL`, иначе
   `entity_not_in_catalog`. Исполнитель gMART сверяет сущности с теми же справочниками.
3. **Переписывание (LLM).** Норма без привязанного плана заново читается по всему пункту (с названием
   документа и breadcrumb) в закрытую структуру `NormSpec` (`norm_spec.py`). LLM не пишет план:
   его строит `SpecCompiler` и отказывает, если сущности нет в каталоге, числа нет в тексте пункта
   (`value_not_in_source`), оператор противоречит шаблону или единица не подходит. Если в пункте есть
   условия или разные значения для разных случаев (тип поселения, этажность, численность, исключения),
   они перечисляются в `NormSpec.conditions` и `NormSpec.variants`: компилируется каждый вариант, и ко
   всем объектам применяется самый строгий (наибольшее минимальное расстояние, наименьшее максимальное
   расстояние или доступность, самый плотный норматив обеспеченности; варианты разного вида —
   `variants_not_comparable`). Такой план остаётся `auto` и содержит `applicability`
   (`mode: strictest_variant`, `conditions`, `variants`, `applied`); gMART помечает его вердикт как
   проверку по самой строгой норме, которую нужно проверить на дополнительные условия.
   Значение, заданное для одного типа жилой застройки (`NormSpec.housing`: индивидуальная — до
   3 этажей, малоэтажная — до 4, среднеэтажная — 5–8, многоэтажная — от 9), проверяется только на
   домах этого типа: план несёт `scope` (слой, атрибут этажности, диапазон, условие), а значения
   для других типов застройки не участвуют в выборе самого строгого. Транспортная доступность
   планируется с `mode: transport` и радиусом при скорости `NG_CHECK_PLAN_TRANSPORT_SPEED_KMH`
   (грубая оценка без дорожного графа, gMART помечает её в отчёте). Нормативы обеспеченности в
   кв. м на 1000 жителей отклоняются (`provision_area_not_in_data`: площадей сервисов в Urban API
   нет), как и число без «не менее/не более» в пункте (`direction_not_in_source`). Названия
   объектов привязываются к каталогу в любом падеже и числе, а формулировки норм
   («общеобразовательные организации» → «Школа», `catalog_aliases.py`) — когда подходит ровно
   один тип. Вызовы LLM получают seed по ограничению, длинный пункт показывается как начало
   (заголовки таблицы) плюс строка самого ограничения.
   Переписывание выполняется до `NG_CHECK_PLAN_REWRITE_VOTES` раз при разных температурах и
   принимается, когда `NG_CHECK_PLAN_REWRITE_AGREEMENT` голосов дают один план (иначе
   `rewrite_votes_disagree`); голос «норму нельзя проверить» завершает проход. Очевидно
   нетерриториальные нормы (миллиметры, материалы, документы…) этот проход пропускают.
4. **Верификация (LLM).** Независимый промпт видит пункт и описание проверки на русском языке и
   отвечает на вопросы `faithful`, `checked_side_ok`, `direction_ok`, `value_ok`, `unconditional`,
   `territorial` (для плана по самой строгой норме вместо `unconditional` — `strictest_ok`); любой
   `false` блокирует план (`verifier_<вопрос>_failed`). Детерминированные
   планы тоже проверяются; планы грамматики точны и не проверяются.

Заблокированный план хранит лучший кандидат в `params.candidate_plan` для ревью. Каждая ревизия
хранит `planner_version` и `trace` проходов (`GET /check-plans/{id}/revisions`).

Шаблоны CheckPlan v1: `distance_from_source` (минимальное расстояние или `source_geometry` для
запрета размещения в границах зон/объектов), `distance_table`, `presence_within`,
`accessibility_within` (пешеходная доступность по времени или длине пути; пока буфер по прямой
`buffer_v1`: `(минуты × 80 м/мин | метры) / 1,3`), `object_attribute_threshold` (этажность, высота через
`floors_to_height_v1`, площадь здания/участка через `geometry_area_m2_v1`), `zonal_attribute_threshold`,
`zonal_ratio` и `service_provision` (места на 1000 жителей или «1 объект на N жителей» —
`residents_per_service`, тогда спрос — все жители, — и доступность из нормы, расчёт ObjectEffectsAPI
`CalculateNormativeProvision`).

`scripts/evaluate_check_plans.py` перепланирует живой корпус офлайн (только чтение: нормы из
NormGraph, тексты пунктов из IDU_DVD) и пишет переходы, причины блокировки и выборку для ревью.
С `--gold scripts/check_plan_gold.jsonl --repeats 3` он вместо этого оценивает планировщик по
размеченным вручную пунктам: точность (автоматические планы, совпавшие с разметкой), полнота
(найденные размеченные планы) и стабильность (пункты, спланированные одинаково во всех прогонах),
с отчётом по каждому расхождению.

`extract_document(..., replace=True)` заменяет ограничения попунктно: старые ограничения пункта
удаляются, только когда его новый ответ LLM валиден. При частичном извлечении упавшие пункты
сохраняют прежние ограничения, остальные получают новые; возвращается `replaced=false`,
предупреждение `replacement_partial`, а id упавших пунктов сохраняются в документе
(`extraction_failed_clause_ids`; в начале прогона список сбрасывается, так что прерванный прогон его
не оставляет). `extract_document(..., clause_ids=[...])` переизвлекает и заменяет только эти пункты.
Структурный ингест до извлечения по-прежнему может удалить пункты, исчезнувшие из изменённого
документа.

## 3. Жизненный цикл синхронизации (`src/sync`)

Держит граф в соответствии с IDU_DVD.

### Kafka-консюмер (`consumer.py`)

Читает топик `document.events` IDU_DVD через **otteroad** (Avro + Schema Registry). Модели событий
(`events.py`) — точная копия моделей продюсера IDU_DVD: otteroad сопоставляет сообщения с хендлерами
по строке схемы из реестра, поэтому они должны совпадать. Хендлеры ставят задачу в очередь
синхронизации (см. ниже) с временем события из брокера:

| Событие | Задача |
|---|---|
| `DocumentProcessed` | новый документ → `sync_name(replace=False)` (ингест + извлечение) |
| `DocumentUpdated` | изменён → `sync_name(replace=True)` (переингест + переизвлечение, чистка устаревшего) |
| `DocumentDeleted` | удалён → `delete_name` (удалить документ/версии из графа) |

Консюмер выключен, пока не задан `NG_KAFKA_BOOTSTRAP_SERVERS`.

### Очередь синхронизации (`queue.py`)

Kafka-события и reconcile только ставят задачи; один воркер выполняет их, **начиная с документа,
изменённого в IDU_DVD позже всех** (время события в брокере, для reconcile — `uploaded_at`). Свежая
загрузка не ждёт, пока разберётся бэклог (массовый перепарс, первый старт), — она обгоняет его
сразу после текущего документа.

Задачи ключуются по документу (имя + `user_id`/`scenario_id`; для reconcile — `doc_id`). Новое
событие по документу, который ещё ждёт, сливается с его задачей: сначала применяются удаления, потом
одна синхронизация текущего состояния IDU_DVD, поэтому порядок событий одного документа сохраняется.
`document_removed=true` отменяет ожидающую синхронизацию. Задача reconcile решает, что делать, в
момент запуска — документ, который уже успело синхронизировать событие, не обрабатывается повторно.

Offset коммитится, как только задача поставлена, поэтому ожидающие задачи хранятся в Neo4j
(`:SyncJob`) и восстанавливаются при старте. Упавшая задача (IDU_DVD или Neo4j недоступны)
повторяется с паузой от 60 с до 15 мин и не теряется. Состояние очереди — в `GET /sync/status`.

### Reconcile при старте (`service.py: reconcile`)

Сверяет листинг библиотеки IDU_DVD с графом по `content_hash`: документы, которые есть в DVD, но нет
в графе — синхронизируются; изменённые — с `replace=True`; исчезнувшие из DVD — удаляются. Документы
просматриваются от новых к старым и ставятся в очередь синхронизации; счётчики результата показывают,
что поставлено (`queued`). Документ,
у которого изменилась только метка версии (IDU_DVD переименовывает версии без события — ручная
правка, `POST /documents/version-repair`), перечитывается структурно, ограничения сохраняются. Один
упавший документ не прерывает весь проход.

Неполностью извлечённый документ с неизменным хешем дообрабатывается: сначала удаляются устаревшие
пункты, затем переизвлекаются только упавшие. Весь документ переизвлекается, если были удалены
пункты (IDU_DVD перепарсил его с тем же хешем) или список упавших неизвестен. Поэтому документ,
который только что переизвлекло событие, стоит лишь несколько упавших пунктов, а не второй проход.

### «Только необработанные события» и guard идемпотентности

Закоммиченные offset'ы при стабильном `group.id` (`normgraph-sync`) означают, что каждое событие
обрабатывается **не более одного раза** между рестартами; otteroad коммитит **после** успешного
хендлера, то есть после того, как задача сохранена в очереди (at-least-once). На первом старте `NG_KAFKA_AUTO_OFFSET_RESET=earliest` один раз проходит
backlog, дальше — только новые события.

Поскольку реплей события (backlog при первом старте, повторная доставка, ретрай, пересечение с
reconcile) может повторно вызвать `sync_document`, **guard идемпотентности** делает это дёшево: при
не-`replace` синхронизации, если документ уже в графе с тем же `content_hash` **и** у него уже есть
ограничения, дешёвый ингест всё равно выполняется, а дорогое извлечение **пропускается**
(`extraction_skipped=true`). Всё, что реально изменилось (новый/обновлённый контент или документ,
загруженный-но-не-извлечённый), обрабатывается.

## Сквозная схема

```text
событие / reconcile / вручную  ──▶  sync_document
   guard (не изменился + есть ограничения?) ──да──▶ только ингест, без извлечения
                                             ──нет─▶ ингест ─▶ извлечение ─▶ ограничения + рёбра
```

### Пространственные планы из полного текста пункта

Явные поддерживаемые формулировки разбираются до LLM. Разбор сопоставляет пункт
целиком: сохраняет проверяемый объект, объединяет интервалы расстояний по этажности
в одну норму и отделяет атрибут здания от названия сущности. Атрибут, интервалы и
число соседей сохраняются в `measurement_json`. Неизвестные названия, условия и
базы расчёта остаются в обычном процессе извлечения и проверки.

`functional_zones` означает все функциональные зоны. Этажность читается из
`building.floors`; отсутствие значения учитывается как непроверенный объект.
Если норма требует контуры, слой должен содержать полигоны: точка школы не заменяет
её контур. Цитаты и числовые значения LLM проверяются по исходному тексту; неверный
ответ делает извлечение неполным и не позволяет удалить предыдущее при замене.
Номер раздела не становится числовым ограничением.

После обновления документы с ошибочными или разбитыми нормами нужно повторно
извлечь через `POST /sync/documents/{doc_id}?replace=true`. Backfill только отсутствующих
планов не исправляет уже сохранённые планы. Для отдельной нормы регенерация помогает,
если сохранена полная исходная цитата. Перед заменой документа учитываются ранее
подтверждённые вручную решения.
